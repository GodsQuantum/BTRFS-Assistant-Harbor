# QA and freeze gates

Environment: Ubuntu 26.04.1 LXC 700 only, Qt 6.10; upstream 2.3.2.
Canonical Cloud9 project directory and Pegasus running backups untouched.

## Implemented and covered

- Fork has distinct Qt executable, desktop ID, polkit action and safely quoted launcher; it stages without writing to system prefixes.
- Remote tab uses upstream Snapper configs/snapshots; manual send, inventory,
  SHA256 verify, staged recovery dry-run with separate confirmation.
- External Harbor CLI is required for main tab. It preserves old archives.
- systemd profiles hourly/daily/weekly with Persistent=true and explicit
  installer; zero units enabled during development.
- Rust CAS prototype with FastCDC 5.0, zstd, SHA256 and BLAKE3, immutable
  chunk files, atomic manifests, corruption refusal and interrupted send reuse.
- Rust CLI enforces explicit experimental flag on new sends, validates
  Btrfs readonly sources, does not shell-evaluate paths.

## Certification absent — production blocked

- No physical end-to-end Btrfs receive/restore test under power loss/SMB/NFS
  disconnect on this LXC's ZFS root.
- No actual 234GiB /home resumability verification or incremental chain proof.
- CAS is integrated as a separately selected Qt mode: init, full/incremental send, list, native verify, and staged receive. Automated CAS scheduling and retention are not implemented.
- Not yet a polished distro package/release, no SSH encrypted CAS transfer,
  recovery browser, actual measured production throughput, or full-metadata
  roundtrip for root/EFI/boot.
- Timers/service executable must be installed with compatible Harbor engine
  before use. No changes to running instances.

## 2026-10-12 (later) completed reproducible real E2E and code hardening

- Rust CAS now records immutable Btrfs source and parent UUIDs and archive
  names; missing/changed parents and cycles fail before receive.
- `Repository::open`, `verify` and `recover` no longer create repository
  object directories on read, even on missing/damaged paths.
- Stream sends retry only transient kernel I/O errors with bounded
  exponential backoff, re-open the repository and revalidate source/parent
  UUID after reconnection; integrity/identity/permission mismatches never
  retry indefinitely.
- Rust resolves `btrfs` through PATH, probes kernel mountinfo directly,
  and works on Alpine where `/usr/bin/btrfs` and `findmnt` were absent.
- `verify-stream` validates Btrfs stream commands/CRCs with
  `btrfs receive --dump` without creating a filesystem volume.
- **Real Alpine QEMU VM**: full and incremental send using the *Rust CLI*,
  CAS archive, restored by the *Rust CLI* through real `btrfs receive` into
  real Btrfs disk, file comparison and Received UUID checks: PASS.
- **Negative real VM tests**: corrupt object and missing incremental parent
  both rejected before a single restore file/subvolume was written: PASS.
- Fully automated end-to-end script, repeatable without extra host mounts:
  `transport/tests/vm/e2e_alpine_btrfs.py`.
- This proves real guest Btrfs correctness on small fixtures. It does NOT
  prove NFS/SMB resumes, physical bare-metal bootable restore, or large-file
  throughput. Fork still experimental and not installed for end users.

## Final validation and remaining gaps — 2026-10-12

Qt now exposes CAS / FastCDC as a separate explicit experimental mode, alongside checkpoint-v2 compatibility. CMake builds and stages the Rust CLI along with the Qt binaries. The external historic Python Harbor CLI is not bundled; it remains a separately installed dependency for checkpoint-v2 operations.

The CAS deduplication implementation was repaired after a red test showed that identical raw chunks encoded at different zstd levels were incorrectly rejected. Reused chunks now verify decoded raw BLAKE3 and persist the already-stored compressed checksum and size. New chunks use zstd level 1 for throughput.

Polkit-root CAS uses PKEXEC_UID as a Linux filesystem UID/GID exclusively during repository operations; the Btrfs send and receive subprocesses retain root privileges. A dedicated LXC700 root-run test showed repository marker, manifest and compressed object all owned by UID1000. Disposable Alpine QEMU guest e2e was rerun with PKEXEC_UID=1000 and passed full and incremental send, native receive, file comparison, corruption and lost-parent negative cases.

Not certified: fault-tolerant NFS/SMB transfers with real disconnects or sleep, production ACL/UID of historic Python scheduled backups, filesystem-spanning EFI/boot recovery, CAS garbage collection, encrypted remote transport and signed distribution.

## Actual network-fault laboratory — 12 October 2026, after alpha3

SUCCESS: real Linux CIFS/SMB3 mount inside disposable Alpine QEMU guest,
Docker Samba backend bound to the LXC700 loopback only. Full and
incremental send, Btrfs native verify, receive, and byte-by-byte comparison
all passed. Two fault types were exercised:
(1) Docker Samba stopped for five seconds during repository preflight:
Harbor's previous non-retry EHOSTDOWN was reproduced and fixed with
bounded preflight retries, then the full test passed.
(2) Docker Samba stopped only after at least three compressed CAS objects
actually reached the server: EAGAIN/errno11 in the initial version
was reproduced and fixed with bounded retry (EIO/errno5 included).
With the corrected code, the in-flight interrupted send restarted, verified,
and restored byte-for-byte. Test harness:
transport/tests/vm/e2e_smb_network_fault.py.

A separate NFSv4 Alpine guest mounted a real NFS-Ganesha userspace server
and completed an initial snapshot chain under the older CAS engine, but a
pause/resume of Ganesha's *MEM* FSAL led to a compressed SHA mismatch.
The new CAS engine reproduced a similar checksum mismatch before committing
even an initial archive on this same in-memory FSAL. This made a
separate **read-after-write, full-object-identity validation before manifest
publication** essential. A new RED then GREEN Rust regression test proves
that modifying an object before commit prevents publication. Ganesha VFS
FSAL could not mount in the restricted nested Docker/LXC environment because
open_by_handle_at requires privileged CAP_DAC_READ_SEARCH; see official
Ganesha VFS documentation. An independent Alpine kernel nfsd guest was
investigated but the harness did not complete successfully; NEVER claim
an NFS reboot/resume test passed. All exploratory resources were isolated
from Cloud9/Pegasus production mounts and stopped after each attempt.

Release status: acceptable as a distinct **Arch alpha4 developer test
package**; not qualified for actual production NFS export, full EFI restore
or scheduled legacy Python ownership. Do NOT install while a previous
Harbor backup is active.
